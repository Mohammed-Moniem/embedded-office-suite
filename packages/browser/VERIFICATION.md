# Browser adapter verification

State: integration SDK implemented; upstream product parity and private-harness acceptance remain unmet.

On 2026-11-07, `node --test packages/browser/test/bridge.test.mjs` passed 50 tests, 0 failed, 0 skipped. `node --check packages/browser/index.mjs` and `tsc --noEmit --strict --lib es2022,dom --module nodenext --moduleResolution nodenext packages/browser/index.d.ts` also passed. The package has no runtime or development package dependencies.

The tests use simulated windows, frames, messages, and host storage. They prove the SDK's routing, envelope, negotiation, save acknowledgement, stale revision, queue, byte-limit, timeout, cancellation, and disposal behavior under those fixtures. They include all four app namespaces, legacy version compatibility, wrong-source/origin/token/version controls, absent page commands, generic-open limits, failed and reversed saves, newer edits during a save, unknown save requests, premature success, missing host storage, navigation and host callback failures. They do not execute Rust/WASM engines or a real WebView and do not establish file fidelity, native platform support, OS sandboxing, complete accessibility, or Office/Acrobat equivalence.

Upstream protocol evidence was read directly from `storytold/craft-libs` commit `2e2312ddaf21bc3d85cd3395d0955c7d239306f6`: `crates/web-host/README.md`, `crates/web-host/src/lib.rs`, and `crates/web-api/src/lib.rs`. Legacy names and optional save IDs match that contract. The page API is a separate engine integration, not inferred from readiness.

Four passes completed: implementation; domain reread against upstream protocol and root integration contract; defect hunt; documentation/API polish. Defect-hunt fixes include pending-save dirty preservation after premature engine cleanliness, reverse-order snapshot rejection, explicit malformed-save failures, open cancellation/readiness deadlines, confirmed-open result validation, generic request byte-limit enforcement, missing-storage capability reporting, and initial-frame load ordering.

Parent verification must rerun this package's exact test file, inspect the actual generated engine builds, and exercise real browser routing and document interactions. Engine extensions must satisfy [ENGINE-PROTOCOL.md](./ENGINE-PROTOCOL.md). Original releases without that extension remain correctly labelled legacy-only, unconfirmed and non-durable by the SDK. Durable host callbacks must be verified in the private harness; a simulated resolving callback does not prove filesystem persistence.

Independent review F1 found that a reply could advance revision while retaining an older revision's clean state. Repaired: an advancing response is conservatively dirty unless an authoritative state notification already established that exact revision. Regression coverage includes response-before-notification and rejection of delayed lower-revision cleanliness. This closes the adapter-side response ordering gap; integration acceptance still requires the parent to re-run its Node/browser close-guard probe.

Storage acknowledgement also preserves the engine's dirty state until its own state notification settles. Writing an exported copy can never, by itself, mark its unsaved source clean. This boundary has a separate regression test.

Independent component review 2 reproduced a cancelled requested save starting its host writer after an older human save finished. Repaired: accepted save operations are linked to their pending request before host observers run; rejection aborts their controllers and sends one engine failure. Queued operations are skipped, and an active callback's late resolution cannot send an acknowledgement. Cancellation request IDs are bounded, never reused, and remain invalid after their tombstones are evicted. Eight added tests cover queued abort and timeout, active abort and timeout, human-save ordering with a non-cooperating writer, late/stale IDs including eviction, duplicate save delivery after successful settlement, engine-request failure, and synchronous observer cancellation. These use simulated storage and messages. Root must re-run actual engine/browser cancellation and acknowledgement cases against this repaired SDK before the integration gate is accepted.

Independent component review 3 reproduced a second observer boundary: saving an already-clean document invoked `onDirty(false)` after storage completed, and synchronous cancellation from that observer caused both failure and success acknowledgements for the same ID. The new abort and timeout regressions failed on those exact contradictory notifications before the repair. Completion now checks operation ownership, cancellation and disposal again after notifying the observer, and only then grants the linked request's save acknowledgement and posts success. Three regressions cover abort, disposal and a timer firing reentrantly from the clean observer. All 50 tests pass after this change. Storage may already have committed at that boundary; cancelled operations remain dirty/uncertain and a late engine success has no authority. These remain synthetic protocol/storage tests, pending fresh independent review and root engine/browser acceptance.
